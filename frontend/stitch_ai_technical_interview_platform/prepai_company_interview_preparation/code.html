Design a High-Throughput Distributed Rate Limiter

Google • SDE-1 Infrastructure • Round 2 • Hard
verified_user
Source Authenticated

Source: Google Campus Placement Drive, Tier-1 Cohort 2024. Confirmed and cross-calibrated by 6 verified candidates with identical architectural parameters.

Problem Statement & Constraints

Design an elastic rate-limiting cluster capable of enforcing API usage limits per client identifier across an edge proxy tier.

• Throughput SLA: 100,000 requests / second
• Max Decision Latency: ≤ 2.0ms p99 SLA
• Cluster Storage: Bounded Redis cluster under 32GB RAM
• Resilience: Graceful fallback mode if cache cluster experiences partial partition
Interviewer Evaluation Rubric
  • check_circle Identification of race conditions (check-then-set concurrency) in distributed counters.
  • check_circle Memory trade-off analysis: Fixed Window vs Sliding Window Log vs Sliding Window Counter.
  • check_circle Clock skew handling across geo-replicated proxy nodes using hybrid logical clocks.
Architecture Blueprint Lua + Redis Atomic Script
rate_limiter_atomic.lua O(1) Memory / Req 
-- Keys: [1] client_id, Argv: [1] now_ms, [2] window_ms, [3] limit
local key = KEYS[1]
local now = tonumber(ARGV[1])
local clear_before = now - tonumber(ARGV[2])

redis.call('ZREMRANGEBYSCORE', key, 0, clear_before)
local current_requests = redis.call('ZCARD', key)

if current_requests < tonumber(ARGV[3]) then
    redis.call('ZADD', key, now, now)
    redis.call('EXPIRE', key, math.ceil(ARGV[2] / 1000))
    return 1 -- ALLOW
end
return 0 -- REJECT (429 Too Many Requests)
