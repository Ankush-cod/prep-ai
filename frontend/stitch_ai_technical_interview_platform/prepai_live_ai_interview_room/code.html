Explain how you would optimize a search operation on a large distributed dataset exceeding 50 TB, where reads are latency-sensitive (p99 < 15ms) and keys follow a heavy-tailed Zipfian distribution.

1. Partitioning & Inverted Index Architecture:

Split the 50 TB dataset across 64 physical storage nodes via consistent hashing with 256 virtual nodes per machine to avoid hotspot skews during scaling. Secondary indices are document-partitioned (local index per node) rather than term-partitioned to bypass multi-node scattered write overhead.

2. Multi-Tier Cache for Zipfian Skew:

Given Zipfian distribution, the top 20% of unique keys service ~80% of read traffic. Introduce an edge distributed Redis cluster (2.5 TB footprint) with an LRU-2 eviction scheme (protecting against sequential scan pollution). Cached values return in < 1.2ms, short-circuiting backend storage queries.

3. Storage Engine & Disk Seek Optimization (RocksDB):

Equip each shard with a local LSM-Tree engine (RocksDB backed by NVMe SSDs). Deploy Block-based Bloom Filters tuned at 10 bits/key (yielding ~1% false positive probability). Non-existent lookups bypass SSTable block decompression entirely, preserving disk IOPS for the Zipfian long tail.

4. Hedged Requests for p99 < 15ms Guarantee:

Tail latency is governed by garbage collection pauses or transient network micro-bursts on shard nodes. Implement client-side hedged requests: dispatch identical search query to a synchronized secondary replica if primary replica response does not return within p95 threshold (9.5ms). Cancel pending task once the first valid frame resolves.
